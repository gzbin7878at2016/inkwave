# 手机与PC纹理分级方案：参考UE4的思路

日期：2026-10-26。基线：v1.0.17功能源码4b11cec。

本轮为源码调查和设计，**没有修改游戏配置、纹理尺寸或APK**。下面的建议值是待验证起点，不是已证实无损的设置。原始日志、APK不随Git同步。

## 1. 先说结论

还有适合做手机单独分辨率的资源。优先调查远景反射、环境反射、海岸距离场，再考虑大厅装饰图集。近处人物、墨迹边界、文字与预警信息需要优先保护。

但要区分三种收益：

- 启动时生成的纹理：缩小后主要可能减少启动耗时、GPU峰值和显存。
- 每帧重画的纹理：缩小后才更可能持续减少填充和带宽；CPU提交绘制的成本未必降低。
- 当前档位没有启用的效果：即使修改尺寸，也不会改善当前这局的帧率。

目前Boss一分钟平均26.18FPS，不能凭纹理缩小就保证达到稳定30。此前采样还发现HUD等CPU开销，需要分别优化。

### 绝不能直接当普通图片缩小的资源

1. **涂墨图集**：手机当前上限2048；`paint.js::_layout`会利用尺寸计算面片布局和密度，CPU墨格与玩法查询也在同一系统中。直接降图集不只是改观感，可能改变墨迹覆盖与判定。只有明确分离逻辑网格和显示纹理后，才可另立方案。
2. **材质参数数据纹理**：`mobileLevelMaterial.js`用最近邻和精确槽位读取参数表。它是数据表，不能像照片一样缩放，否则材质映射会错误。
3. **烘焙AO/lightmap图集**：UV、padding和布局哈希有约束，直接缩图可能漏光/串色。要走资产生成和图集边距验证，不列入首批。
4. **最终画面、人物、准星、HUD文字、Boss攻击预警和射击反馈**：优先保留2倍/SMAA及可读性，不能通过缩主画面伪装优化。
5. **阴影**：手机默认已关闭。先核对运行状态；关闭时调小shadowSize不会自动产生持续帧率收益。

## 3. UE4怎么处理这种差异？

UE4的思路很适合借鉴：对同一个游戏，按设备选择表现预算，同时保持玩法规则一致。它的移动渲染路径本身也与桌面不同。[UE4.27移动渲染](https://dev.epicgames.com/documentation/en-us/unreal-engine/mobile-rendering?application_version=4.27)

### 设备档案：决定“这台设备用什么预算”

UE4用Device Profiles匹配设备与GPU家族，并允许继承基础档案、增加特殊兼容规则。我们可仿照建立PC原版、手机标准、手机保守、手机高档；未知手机先用保守配置。不要照搬UE4当年的GPU名单来判断2026年的设备性能。[UE4.27 Android设备档案](https://dev.epicgames.com/documentation/ko-kr/unreal-engine/customizing-device-profiles-and-scalability-for-android?application_version=4.27)

### 画质伸缩：每组功能有自己的档位

UE4分别管理纹理、阴影、后处理等质量，也提供材质质量切换。我们应把画面密度、环境烘焙、反射、装饰纹理、战斗反馈分别管理，避免一个low同时降低所有东西。UE4也明确提醒，细节伸缩只能用于不影响玩法的对象。[UE4.27伸缩参考](https://dev.epicgames.com/documentation/en-us/unreal-engine/scalability-reference?application_version=4.27)

### 每设备纹理LOD与通道打包

UE4.27支持按设备设置纹理LOD，并建议减少纹理采样、按用途管理颜色空间及通道。我们已有ORM打包，可以保留；新增分组时应按“环境装饰/近景人物/界面/数据表”区别对待。[UE4.27手机纹理](https://dev.epicgames.com/documentation/en-us/unreal-engine/textures-for-mobile-platforms?application_version=4.27)

### 可以借思路，不能直接搬引擎配置

本项目是Three.js/WebGL2加Capacitor，不会读取UE4的ini或r.*控制台变量。UE4的反射压缩、纹理流送、原生移动渲染器也不会自动存在。

UE4文档里的PVR/2048限制针对其特定管线，不是所有Android/WebGL纹理的统一上限。此处云纹理512×160在WebGL2中可用，不必因UE4文档就强改成正方形。

静态资产以后可另评估KTX2/Basis压缩，但需转码器、扩展检测和回退；运行时生成的HalfFloat反射目标不能靠给PNG加压缩参数就变成压缩渲染目标。首批先做尺寸分级，避免同时引入复杂资产管线。

## 4. 我们的移植设计

以下为拟新增结构，不表示文件已存在：

```text
src/platform/renderProfiles.js  档案与继承、校验、版本号
src/platform/textureBudget.js   资源登记、尺寸、估算内存、生命周期
现有环境/大厅/纹理工厂         创建资源前读取对应分组预算
现有诊断系统                  输出最终生效值和选择原因
```

执行规则：

1. PC入口明确选择pc-original，逐项保留现有值和原有画质选择逻辑。
2. 手机先使用mobile-standard，其云图沿用已验证512×160；反射等候选值未通过前保留现值。
3. 设备档案只覆盖允许的表现资源；不得改变命中、移动速度、墨格、碰撞、人数、Boss攻击时间。
4. 将“能力限制”和“性能档位”分开：支持大纹理不代表跑得快；渲染器名称不可用时仍有安全默认，不能只按品牌或内存选档。
5. 选择顺序写死为：平台原设置 → 已批准设备档案 → 用户允许的表现选择 → 硬件能力/兼容限制。用户不能强行越过硬件限制；PC不应用手机覆盖项。
6. 在启动/换场景时应用尺寸，不在战斗中反复销毁重建RT。将档案版本和尺寸写入缓存键，旧资源解除绑定后按生命周期释放。
7. 诊断记录资源名称、实际尺寸、格式、层/面数、mip、更新次数、估算字节、是否启用及生效档案；不把未创建资源记成正在消耗显存。
8. 内存数字标明估算，不称为实际GPU总显存；还要考虑深度附件、多缓冲、驱动开销与临时烘焙资源。

示例：远景512立方体RGBA16F，基础颜色约512×512×6×8=12MiB；带完整mip约16MiB。改为256后约4MiB。这里不含深度和临时资源，不能把它当作整机净省12MiB的实测结果。

## 5. 怎样做到统一的游戏体验？

统一的是玩家能看清的信息和游戏规则，同时允许远景等次要细节不同：

- 玩法一致：相同地图几何、碰撞、命中、移动、墨迹判定、Boss时序和人数。
- 战斗信息一致：队色、敌我轮廓、预警范围、准星、伤害反馈保持可辨识；反射和装饰不能成为唯一信息来源。
- 美术方向一致：配色、光照方向、水墨风格、主体轮廓一致，远云与倒影细节可分级。
- 输入响应和稳定性有预算：30FPS每帧约33.3ms；不能只看平均值，要同时看p95/p99及100ms尖峰。

特别注意：远景图低一点通常比人物模糊更不显眼，但“不影响体验”必须通过截图和真机游玩验收，不能靠名称判断。海岸距离场虽然不直接修改CPU碰撞，也可能使显示的水边与可行走边缘不一致，必须检查。

## 6. 分批执行与验收

每批只改变一个主要变量，先基础检查、中文commit/push，再从干净提交构建APK。结束后单独提交测试结论；失败就回退该项，不累积未验证降档。

| 批次 | 如何做 | 验证重点 | 人工开发估时 |
| --- | --- | --- | --- |
| A：运行清单 | 给现有资源添加轻量诊断登记，记录实际创建/尺寸/更新频率；不改变尺寸 | 当前Boss、marina、大厅分别有什么资源；诊断不能每帧同步读回GPU | 0.5～1天 |
| B：档案基础 | 建立平台档案/分组/校验，先复现现值，接入云图和远景反射 | PC参数与画质路径一致，手机2倍/SMAA不变，重复切图无资源泄漏 | 0.5～1天 |
| C：远景反射 | 仅手机512→256，其他现值不动 | marina远山/灯塔倒影、主题切换、启动峰值和内存；没创建此资源的Boss不计收益 | 0.5～1天 |
| D：环境PMREM | 手机输入256→128单变量 | 固定相机下人物、椅子、金属和水墨亮度；室内/日落/夜景均看 | 0.5～1天 |
| E：距离场 | 泡沫和甲板距离场分两次改；映射参数随尺寸同步 | 浮标、船边、窄码头、落水边界；仅命中对应路径才有效 | 1～2天 |
| F：装饰资产 | 大厅和壁画按用途拆组、按档案生成；UI/重要文字保留 | UV矩形、padding、字体、mip串色、近远距离；不只缩canvas而忘记坐标 | 1～2天 |
| G：长时与跨设备 | 一分钟迭代通过后，再做长时与不同GPU验收 | 热机稳定、显存增长、前后台恢复、PC回归、联机可读性 | 1～2天 |

估计完整方案约5～10个工作日；先完成A～C约1.5～3天。按一天约8小时粗估，视手机/网络/签名和故障复现情况变化，不是自动执行的完成承诺。

每个候选的测试步骤：

1. 留存基线APK和源码；记录手机、系统/WebView、画质、地图、主题、电量与温度条件。
2. 固定地图、随机种子（工具支持时）、相机、操作和人数；不支持固定的随机项明确记录。按基线→候选→基线交错比较，避免把温度或随机场景当成收益。
3. 三次冷启动，保存真实画面和原生日志；不能只相信网页Ready状态。
4. 对应地图先截图验视觉，再跑一分钟Boss或对应实战；不要只测Boss来验收marina专属资源。
5. 采集CPU分段、帧间隔和绘制统计。有可用GPU计时扩展时异步采样并剔除disjoint数据；不可用时明确未测GPU耗时，不用JS提交时间替代。
6. 查看p50/p95/p99、100ms尖峰、初始化错误和资源数量。若只省内存/启动，就按该收益记录，不虚报提帧。
7. USB上传，核对电脑JSON版本/源码和落盘，再关闭游戏。保存通过、失败、视觉差异及回退结论。
8. PC默认及各原有画质档对比；人物、文字、墨边、预警不能明显劣化，不能新增图形错误。达到此轮标准才接下一项。

第一批实施应从A开始，取得运行资源清单，再决定是否先做远景反射；不要一次性把表内所有建议值都应用。
