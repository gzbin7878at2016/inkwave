# Opus 性能修改说明：改了什么、为什么改、目前验证到哪一步

更新日期：2026-10-27。本文根据实际 Git 差异整理，方便项目负责人了解另一台电脑提交的修改。

## 1. 先看结论

这次有两项产品优化：

1. **手机 Boss 小地图的后台计算线程遇到短暂超时后，可以恢复使用。** 原来一次超时会让它在本局剩余时间永久停用；现在先用原算法补画，等旧任务处理完，再恢复后台计算。
2. **手机实战中的普通诊断日志暂存在内存，离开战斗后再写入浏览器本地存储。** 减少战斗期间同步整理、序列化和写入整份日志的工作，同时去掉一次不必要的性能快照计算。

这次没有修改游戏分辨率、SMAA 抗锯齿、人数、武器伤害、Boss 血量、AI 或物理子步，也没有通过降低这些要求换取帧率。

**源码行为验证已有另一台电脑的通过记录，但尚未用这批代码构建新 APK 并验证手机性能，不能宣布稳定30帧或具体提升百分比。** 本机已拉取到合并提交；手机此前安装的正常体验包仍是合并前的代码。

## 3. 优化一：小地图 Worker 从“永久退出”改为“临时停用后恢复”

### 3.1 先理解主线程与 Worker

可以把主线程理解成游戏现场的工作人员：处理玩家输入、推进游戏、准备渲染，还要更新界面。它忙不过来时，画面就容易卡。

Worker 是额外的后台工作人员。项目此前已经把手机 Boss 小地图的部分像素计算交给 Worker，主线程接收结果后更新小地图。这次不是新加多线程，而是修正这套已有机制的恢复策略。

### 3.2 原来的问题

原代码有保护：最旧的待处理结果超过 **3帧或250毫秒**，就判定结果过旧，立刻切回原来的同步小地图算法，避免使用落后的数据。

保护本身有必要，但旧处理方式会直接销毁 Worker。本局余下的小地图计算都回到主线程，即使超时只是一次短暂卡顿造成的，后台计算也不会恢复。

这相当于：后台工作人员偶尔迟到一次，就让他整天停工，后续所有工作都交给本来就忙的现场人员。

**超时不一定代表 Worker 自己计算了250毫秒。** 任务排队、线程调度、主线程没及时接收结果等，也可能使结果变旧；本次修改没有证明所有超时的根因。

### 3.3 新代码怎么处理

处理顺序如下：

1. 发现超龄、队列积压，或者已准备好的 Worker 遇到暂停/切后台时，先进入 `parked`（临时停用）状态。
2. 保留 Worker，把尚未完成的旧任务标记为作废。
3. 需要补图时，使用原来的主线程算法，保证画面数据有正确来源。
4. 旧结果返回后，只回收缓冲区，不把旧像素覆盖到新地图上。
5. 等旧任务排空、必要的整图补画完成，并且游戏已恢复运行后，重新启用 Worker。
6. 恢复的第一段计算携带主线程当前的归属、墨迹和闪光数据副本，使双方从同一状态继续计算。

同步使用副本，不转移主线程正在使用的真实地图缓冲区，避免主线程数据因转移而失效。复制和重新同步仍有成本，实际收益取决于停用发生频率、恢复速度及手机负载。

### 3.4 保护有没有被放宽

没有。**3帧、250毫秒、最多3个在途任务的保护仍保留。** 变化是如何处理短暂失效，而不是允许使用更旧的结果。

真正异常、地图数组重建、配色或强制重画触发的失效、离局和换局等情况，仍会终止 Worker。准备过程中遇到暂停也仍可能终止，不是任何情况下都保留。

### 3.5 预计有什么帮助

它主要防止“一次长帧导致后续整局持续增加主线程工作”。如果某局此前经常永久回退，新策略可能改善后半局的持续性能，以及暂停返回后的性能。

它不能直接消除触发超时的原始长帧，也不能保证恢复后永不再次超时。如果一局原本没有发生永久回退，收益可能很小。

### 3.6 新增统计怎么读

| 字段 | 含义 |
| --- | --- |
| `parked` | 当前是否临时停用 |
| `parks` | 临时停用次数 |
| `resyncs` | 排空并恢复次数 |
| `dropped` | 已返回但作废、仅回收的任务数 |
| `fallbacks` | 终止并降级的次数；不能再把它理解为所有临时补画次数 |
| `fallbackFullDraws` | 同步整图补画计数，需结合原因判断 |
| `maxAgeMs` / `maxAgeFrames` | 记录到的最大结果年龄，仍用于正式验收 |

诊断时要一起看这些字段。仅看到 `fallbacks=0`，并不代表从未超时或从未同步补画。

## 4. 优化二：实战普通日志先留内存，减少同步落盘

### 4.1 原来的问题

诊断系统原本会定期整理场景，每5秒保存整份报告；普通事件还可能安排1.5秒后的保存。

保存包含 `JSON.stringify`（把对象转成文本）和 `localStorage.setItem`（写入浏览器本地存储）。这些操作在主线程同步执行，做完之前主线程不能继续正常处理后面的工作。报告越大，潜在成本越高。

这里的“落盘”指写浏览器本地存储，不是每5秒通过 USB 把 JSON 文件传给电脑。USB上传仍是用户主动触发的独立动作。

### 4.2 新代码怎么判断战斗

满足以下条件时视为实战：当前模式为 `match`，对局状态为 `playing`，不是演示对局，而且没有暂停。

**这项优化覆盖手机正常实战，不只限于 Boss。** Worker 恢复策略则有手机、真实 Boss 和当前对局归属检查，范围更窄。普通 PC 网页/桌面原入口不安装本次移动诊断入口，不能把桌面模拟手机环境与普通PC路径混为一谈。

### 4.3 不同日志什么时候保存

| 情况 | 新行为 |
| --- | --- |
| 实战普通 `info` 记录 | 继续记录在内存，暂缓写本地存储 |
| 实战5秒场景快照 | 继续采集并保留在内存，不为普通周期强制保存整份报告 |
| `warn` / `error` | 仍安排约1.5秒后保存，保留异常取证能力 |
| 暂停、结束或回菜单 | 在诊断下一次正常 tick 中补存；未到5秒周期也能补存 |
| 页面隐藏或离开 | 按原事件路径立即尝试保存 |
| 着色器失败、上下文丢失等关键异常 | 保留原立即保存路径 |
| 用户导出或上传 | 保留原主动保存/导出路径 |

浏览器定时器不是硬实时保证；1.5秒表示安排延迟，主线程卡住时实际执行可能更晚。

### 4.4 额外删掉了一次无用工作

原来的场景事件快照会先调用完整性能资料快照，再把其中的 `profile` 字段删除。被删掉的内容不写进事件，但生成它的工作已经做了。

新代码增加 `sceneSnapshot(false)`，生成这种事件时直接跳过性能资料快照。完整报告保存仍可包含原来的资料，不是删掉所有性能统计。

### 4.5 需要知道的取舍

如果游戏在战斗中直接崩溃，且没有触发页面隐藏、保存或异常路径，尚在内存里的普通日志可能丢失，下一次启动无法恢复这些未保存内容。

警告和错误仍保留保存策略，但突然崩溃发生在安排的保存执行之前，也不能保证所有记录已经写入。这次是在实战流畅度和普通日志的即时持久化之间做取舍。

## 7. 后续怎样判断优化是否有效

目前用户已暂停Boss优化，以下仅为恢复工作后的验收建议，不会因生成本文自动启动测试。

1. 先在Windows复跑相关源码行为测试，确认与另一台电脑一致。
2. 从干净提交构建、核对版本/签名/哈希并安装新APK；仅拉取代码不会更新手机游戏。
3. 方法轮检查一次停用后能恢复，旧数据不覆盖小地图；观察 `parks/resyncs/dropped`，不能只看 `fallbacks`。
4. 检查普通战斗期间本地存储写入次数，区分主动导出和警告/错误保存；确认暂停、结束和上传内容完整。
5. 在相近温度、同画质、同人数和相同游玩方法下交错比较新旧版本，每局一分钟；同时比较平均帧率、P95/P99帧耗时、长帧、Worker状态和温度。
6. 方法探针与正式成绩分开。按现有门槛判定，不将有超龄的轮次包装成稳定成绩；每轮上传核对后按既定流程关闭游戏。

最值得关注的是：**一次卡顿之后能否持续恢复后台计算，以及诊断本身是否减少对战斗主线程的打扰。最终有没有明显提帧，需要新APK真机数据回答。**
