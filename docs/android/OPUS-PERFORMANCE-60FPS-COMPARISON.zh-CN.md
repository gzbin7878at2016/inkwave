# Opus优化：60帧上限下的新旧真机对比

日期：2026-10-27（北京时间）。用户明确要求解除前次30帧上限，再对比同一对新旧APK。此为有限测试，不恢复无人值守持续优化。

## 结论

**本次没有测出Opus两项修改带来的明确性能提升，也没有达到稳定60FPS。**

旧版两轮平均 38.63199 FPS，新版两轮平均 38.04394 FPS，新版观测值低 0.58806 FPS（约1.52%）。这里只是每轮平均FPS的算术平均，不是控制温度、随机种子后的严格因果估计。温度、阵容和战斗负载不同，样本各两轮，不能据此宣布确定的性能回归，也不能将长帧减少解释成稳定收益。

此前30帧测试的上限确实会遮住部分吞吐差异；本次已通过实际诊断确认四轮fpsCap都为60，实际平均约36～40FPS，并非仍在30帧上限下运行。

## 本次中断：UE4与项目ADB版本互相重启

无效轮 `opus60-new-B1` 在约7秒游玩后CDP断开，未完成自然结算、未成功上传；最终已force-stop确认关闭。此轮没有完整FPS结果，不纳入均值，原始报告仍保留。

直接证据：日志出现 `adb server version (40) doesn't match this client (41)`；进程父子关系显示UE4Editor.exe（另一个LuaSocial项目）反复调用 `J:/UE4_Android/android_sdk/platform-tools/adb.exe`，它的ADB为1.0.40 / 28.0.2，而本项目隔离工具链ADB为37.0.1、协议41。两种客户端争用5037，服务重启使9223转发和USB reverse失效。

恢复方式：不关闭UE4、不改它的SDK/JDK/全局环境，也不操作驱动；本次后续命令进程设置 `ADB_PATH=J:/UE4_Android/android_sdk/platform-tools/adb.exe`，`start-usb-debug.ps1 -AdbPath`也指向同一客户端，再建立reverse。B1重测/B2/A2均完成，没有再见该冲突。这里仅解释本次有直接证据的断连，不推断所有历史USB故障都是相同原因。

以后UE4仍打开时，应先核对当前5037服务版本，避免用两套不兼容客户端反复devices/kill-server；本地路径不是跨电脑固定配置。

## 如何评价Opus修改

- 前次已经证明Windows诊断保存行为，以及真机原暂停/继续后Worker确实恢复。这些行为证据仍有效，见[v54前次报告](BOSS-PERFORMANCE-test54.zh-CN.md)。
- 本次在60帧上限下仍未测出明确提帧，也没有发现通过降低画质制造收益的情况。
- 诊断保存与Worker恢复是同一新版一起测的，本次没有分别开关，不能归因某一项贡献了多少FPS。
- 是否值得保留，可依据其避免一次异常后永久降级的合理性和行为检查；不能以本次数据宣传“性能已提升”。未来若需要更强结论，应在同温度段重复多轮，单独采集实战存储写入，并覆盖自然超龄场景。

测试结束：旧版回测后已覆盖安装回v1.0.54，游戏保持关闭；持续自动优化仍暂停。未稳定60帧，不自动启动下一轮优化。
