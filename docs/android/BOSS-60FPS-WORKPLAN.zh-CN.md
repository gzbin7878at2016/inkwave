## 2. 当前判断、约束和目标

### 2.1 优先追查的证据

新版热机轮的滚动采样窗口中，模拟阶段典型中位耗时约6.2ms，部分窗口P95达到14.4ms；捕获的一帧总耗时119ms，其中模拟阶段101.2ms、draw约5.2ms、UI约10.9ms，programsAdded=0。

这是明确的定位入口，不是已经证明Boss AI独占101ms。模拟阶段包括控制器、角色、Boss、弹丸等；计时使用JS墙钟，可能包含GC、被系统抢占及其他等待。

draw常见约4～6ms，代表JS/驱动提交路径，不是GPU完成时间。HUD也有成本，浏览器在JS回调之后可能继续进行样式、布局、绘制和合成。不同窗口/阶段的P95不能相加，历史Trace也不能直接当作最新版每帧预算。

本计划第一优先级：**拆清模拟普通耗时与长尾，并解释游戏阶段计时和最终掉帧之间的缺口。** CPU、GPU、浏览器合成、调度和工具成本分别举证。

### 2.2 所有批次必须保持

1. 仅处理手机真实Boss路径；PC普通网页/桌面及其他场景保持原效果。
2. 固定2倍高清、SMAA、8人、原玩法、AI决策与物理子步；动态降清晰度关闭。
3. 60FPS是测试上限，产品默认设置保持原值，除非用户另有要求。
4. 不改伤害、血量、墨资源或模拟时间制造相同负载/漂亮数据。
5. 不以减少人数、降低AI频率、跳过关键姿态/物理更新、隐藏HUD或关闭音画作为正式优化成绩。
6. 不放宽Worker 3帧/250ms保护及现有正式轮门槛；需要调整门槛应单独提出依据，不在测试中暗改。
7. 不修改全局温控、性能模式或UE4工具链，不root，不使用隐藏系统接口。
8. 每轮60游戏秒，实际游玩、自然结算、真实上传核对落盘、再关闭游戏。

### 2.3 拟定的60帧验收目标

以设备实际60Hz且设置60FPS为前提，建议使用以下工作验收线；实施前应在报告中固定口径，不能看完结果再改：

- 正式一分钟整局平均FPS至少59；P95帧间隔≤18.5ms、P99≤33.4ms，≥100ms长帧为0。
- 不只看整局平均：逐秒/短窗口不得出现持续一段时间的30帧或更低平台；所有低值如实列出。
- 同一候选至少3个有效正式轮通过，并有相近温度对照；只达到冷机目标不能宣布持续稳定。
- 实际覆盖普通射击、移动补墨、密集危险物、大招，以及阶段1/2/3；缺某项则该项待验，不能写“Boss全场景通过”。
- 图形无错误/致命降级，原玩法、退出恢复、USB日志及缓冲回收检查通过。

这些是建议的项目门槛，不是保证每帧绝无波动。若要更严格地宣称“锁60”，还要检查实际呈现帧与更长时间分布。原脚本的status=measured只表示采集完成，不代表上述60帧门槛通过。

## 4. P00：固定环境与对比方法

### 如何做

1. 读取最新交接，执行 `git status --short`、`git branch --show-current`、`git remote -v`，核对用户仓库与分支。
2. `git fetch fork`，检查HEAD与远端分叉；仅无分叉且无受影响本地修改时fast-forward。保留用户Logs/及私人bat。
3. 检查是否已有测试进程和9223转发拥有者；已有任务时先确认归属，不启动第二个CDP拥有者。
4. 使用同一ADB客户端检查手机。UE4正在调用协议40的旧ADB时，当前命令进程使用同一客户端，避免协议41客户端反复重启5037。其他电脑必须重新检查路径与版本。
5. 用 `tools/start-usb-debug.ps1 -AdbPath ... -Serial ...` 建reverse，手机USB供电常亮；不更改UE4全局环境。
6. 核对APK哈希、安装版本和日志中的sourceCommit。不能把仓库HEAD当成当前手机APK源码。
7. 固定设备朝向、充电方式、屏幕刷新率、温度分组和同一Director revision；普通正式轮关闭所有实验/方法探针。
8. 取相近起始电池温度，建议差≤1°C；记录结束温度、系统热状态及可读取的频率信息。超出温度组的轮次另列，不能删掉或冒充同温。

### 注意点与产物

电池温度不是GPU温度；频率降低也不能只凭电池温度证明热降频。只读策略工具可用 `tools/capture-phone-cpu-policy.mjs`，读取失败则记录不可用，不提权硬取。

交付一张环境/版本/参数表和唯一测试名称清单。基础环境不能可靠复现时先修测试链路，不进入产品优化。

## 5. P01：将模拟耗时拆到可以行动的粒度

### 修改范围

优先扩充有界性能记录或独立方法工具，入口位于 `src/main.js` 的 `_frame`、`src/game/match.js` 的updateController/update及相关Boss/战斗系统。具体插点必须读实际调用关系，不凭名称推断。

### 如何做

1. 列出一次游戏帧的调用树：控制器→原物理子步→队友AI/角色/Boss→弹丸/副武器/大招。明确哪些在每子步运行、哪些只在整帧运行。
2. 给同一帧记录编号、实际dt、子步次数；按父子阶段分别统计，避免把父层包含耗时和子层耗时相加。
3. 记录AI、角色物理/武器、Boss决策/移动/攻击、危险物、弹丸、副武器、大招的有界耗时汇总，并附活跃数量。
4. 覆盖每帧长尾识别，但常规细节低频采样；使用固定容量环形缓冲，只保存最慢若干条，不逐帧JSON.stringify、写文件或console输出。
5. 单独计入自动Director的决策/路径规划及注入开销；它在原 `_frame` 之前的工作不能遗漏。标明“游戏本体”和“测试驱动”两个范围。
6. 记录原始rAF回调间隔、经过mobileFrameDue后真正执行游戏帧的次数和跳过次数，判断是回调迟到还是应用限速逻辑跳过。此时只观察，不先改限速算法。
7. 关联程序创建、GC/系统事件时间戳；不要因为programsAdded=0就断言没有驱动等待。
8. 先做桌面针对性正确性/开销检查，再提交推送，再构建安装；方法轮检查探针对帧率和长帧的影响。

### 验收与决定

- 输出普通帧和长帧热点各一张表，包含调用频次、包含/自身范围、活跃数量、温度及来源。
- 能解释119ms慢帧所属的模拟分支，或明确它主要是GC/被抢占而非该函数纯计算。
- 探针明显扰动则减少范围/窗口重新验证，不把该轮作为正式成绩。
- 无可复现热点时进入P02补证据，不直接重写AI或整体Worker化。

## 6. P02：解释最终帧间隔，而不只看JS函数时间

### 如何做

1. 采集一轮独立METHOD_PROBE=1正常游戏。浏览器Trace使用既有工具，先阅读参数和已有调查约束；辅助工具只附着9223，不创建新转发。
2. 使用短而窄的窗口，对齐实际游戏帧、慢帧、GC、样式、布局、绘制、合成和提交。禁用曾导致超大数据的详细Skia长采集，禁止请求 `/json/protocol`。
3. 对需要的短窗口采集原生调度/频率，核对本轮WebView PID/TID、记录完整性和实际时间范围；缓冲丢失/目标错页的采集标为无效。
4. 区分：主线程忙于计算；线程就绪但没获得CPU；GC暂停；浏览器样式/合成；驱动/呈现等待。缺少GPU计时能力时明确“GPU未独立测得”。
5. 比较探针开关的相近温度轮次。历史V8启动曾制造约1.3秒停顿，不重复将它当产品问题；不长期开启重采样做正式测试。
6. 若工具Director占比显著，补充正常触摸游玩验证；不添加与玩法无关的假触摸刷系统性能，不把测试脚本优化当产品优化。

### 输出与分支

输出普通慢帧和长尾的证据链：游戏帧号→阶段→系统事件→可能原因→尚未排除因素。

- 模拟纯计算/分配最重：进P03。
- 渲染提交最重：进P04-A。
- GPU/合成限制更强：进P04-B。
- 调度/热策略是主要限制：先降低持续工作量并复测，不能依赖强制系统性能模式验收。

## 7. P03：一次只做一项已确认的模拟热点优化

### 候选操作

按实测热点选一项，不一口气全部做：

1. 临时对象/数组分配重：复用缓冲和向量、避免重复filter/sort等；先证明分配位置和生命周期，不看到new就盲目对象池化。
2. 相同物理步重复查询：在输入、地图版本及时间范围一致时复用结果；跨子步必须重新验证失效条件，不能省掉应更新的数据。
3. 静态地图衍生数据重：加载期预计算，几何/地图/配色变化时失效，限定内存预算并正确释放。
4. 查询范围重：只优化证明过宽的候选集合，最终命中结果、顺序和边界保持；现有空间网格已存在，不能重复“新增网格”当成果。
5. 战斗中创建资源重：迁到有进度反馈的准备期，核对取消/重开/离局清理；不把负载转移成新的初始化失败。

### 验证步骤

1. 为被改入口定义不变量：相同输入下的位置、碰撞、命中、伤害、冷却、墨资源、事件/随机数调用顺序等。不是每项都需新测试，但相关项必须有证据。
2. 用真实入口和有代表性的固定输入验证；测试固定随机源只用于测试环境，不改变产品随机行为。
3. 验证死亡/重生、暂停继续、换局、阶段切换、离局清理、PC/其他模式隔离。
4. 基础检查通过后中文commit/push；从干净提交构建安装，方法轮确认优化确实命中，不只是缺少该攻击/武器。
5. 正式新旧ABBA，至少各2轮先筛选，温度/负载不足可比时追加匹配轮次并保留所有结果。
6. 同时看目标阶段与整局：局部下降但最终无可靠收益，记录原因，不自动扩大修改范围。

### 失败处理

结果不一致或有玩法差异则不验收。需要撤回时新建中文回退提交并推送，不能强推或删除已有优化过程。没有收益的候选记入负结果，避免以后换电脑重复试。

## 8. P04：根据证据选择渲染分支

### P04-A：CPU渲染提交重

1. 按真实绘制/材质/对象统计确定成本，区分可见与隐藏、静态与动态，不只按三角形数量排行。
2. 查重复遍历、重复材质参数写入、重复缓冲上传；缓存必须覆盖相机、对象、动画、材质变化的失效。
3. 对必要的合批/剔除改动，先在真实固定场景、多个视角做原/候选/重复/恢复像素与状态检查，再测提交时间。
4. 保持透明物绘制顺序、深度和阴影语义；不得为省遍历跳过影响枪口、命中或动画事件的矩阵更新。
5. 手机有稳定收益才进入产品。已有props多绘制、隐藏LOD、射线缓存等负结果先读对应报告，不原样重做。

### P04-B：GPU或浏览器合成重

1. 先确认GPU/合成等待与漏帧的对应关系；JS render耗时、gl.finish墙钟、GPU服务线程CPU都不能单独冒充纯GPU计时。
2. 检查透明覆盖、全屏特效、材质和后处理；按实际屏幕覆盖与有效调用测，不仅看对象数量。
3. 第一阶段保持视觉，优先冗余工作消除。已有SMAA合并/RG16F等实现需保留验证，不能重复计算已获得的收益。
4. 清漆、手机专用简化材质或粒子视觉预算属于有画面取舍的后备方案；先说明视觉差异，用户决定后才实施，不偷偷降2倍/SMAA。
5. 资源/渲染状态按手机真实Boss入口启用，暂停、退出和PC路径恢复有检查。

验收要求：有可重复的成本下降和正式轮收益；固定场景耗时不是整局FPS，方法轮隐藏/关特效不是产品成绩。

## 9. P05：剩余UI、内存和长尾预算

只有新排行显示这部分仍值得处理才做，不重复已否定的CSS选择器、名牌图像缓存或可见动画降档方案。

- 对未变化的DOM值减少写入，验证显示时机、数值精度、状态切换和布局一致。
- 有界复用临时内存，检查池容量、保留内存和清理，不能用持续增长换短时收益。
- 将普通诊断写入按“playing/暂停/结束/警告/用户上传”分别标记，只给计数不保存敏感全文；验证Opus日志策略实际生效。
- 对每次≥100ms长帧保留归因证据，不能只优化P50而让死亡/重生、大招、阶段切换仍卡顿。

## 10. P06：最终验收与时间安排

1. 候选先完成各2轮ABBA筛选，达标趋势明确后补足至少3个有效候选正式轮。
2. 每轮继续60游戏秒，上传确认后关闭，再启动下一轮；用15～30分钟的重复短局观察温度与长期趋势，记录实际游玩/启动/间隔时长。
3. 上述重复短局**不等于单局连续运行15～30分钟**。如需连续长局，应单独取得用户对延长单局的要求；不能违背既有一分钟约定。
4. 第三阶段在自然一分钟内未出现时，明确缺项；可改进合法游玩策略再试，不强制跳阶段或修改Boss血量。无法覆盖时单独提出后续验证安排。
5. 按第2.3节统计整局和窗口，不只看瞬时FPS；同时核对图形错误、稳定性、暂停/后台/退出恢复、USB落盘。
6. 只有全部适用验收通过才写完成。平均59以上但热机持续掉到30、缺第三阶段或有100ms长帧时，记录“部分通过/待验”，不标目标完成。

## 14. 方法参考

- [Chrome Performance帧时间线](https://developer.chrome.com/docs/devtools/performance/reference)：区分正常、部分呈现和丢弃帧。
- [Android慢帧原因说明](https://developer.android.com/topic/performance/issues/slow-session)：CPU/GPU、热限制与帧率匹配需分别分析。
- [Android Thermal API](https://developer.android.com/games/optimize/adpf/thermal)：热状态作为性能上下文，不凭电池温度单独判定根因。

Android原生Swappy等资料用于理解时序；本项目是Capacitor/WebView，不能直接把原生引擎库当作一个配置开关接入。新增原生方案需要单独验证适用性。
