# 云层烘焙负载过高：新手说明

更新日期：2026-10-26。适用项目：DemoInk / INKWAVE，当前说明对应 Android v1.0.17。

先记住一句话：**游戏要先用手机的图形处理器算出一张云的图片，之前这项工作与其他启动任务叠加时，可能让当前测试手机的图形系统承受过大的瞬时压力。** 现在只降低手机这张云图片的尺寸，游戏的“2倍高清”和PC原有设置仍然保留。

## 1. 先认识几个词

| 词语 | 可以怎样理解 |
| --- | --- |
| GPU | 图形处理器，擅长同时计算大量像素，负责把场景画出来。 |
| 纹理 | 给渲染使用的图片，例如衣服图案，或者本次生成的云图片。 |
| 着色器（shader） | 在GPU上运行的小程序，用来计算颜色、光照等效果。 |
| 烘焙 | 先把复杂计算的结果保存成图片，之后绘制场景时再使用这张图片。这里不涉及实际加热。 |
| 离屏渲染 | 先画到一张内部图片上，而不是直接画到手机屏幕上。 |
| WebView | Android应用里运行网页内容的组件。我们的游戏通过它使用图形系统。 |

## 2. 为什么云还要“烘焙”？

想象你要画一片有很多层次的云。如果每次需要云彩，都重新做一遍复杂计算，就可能重复花费很多力气。另一种做法是先算好一张云图，后面的天空渲染再使用它。这就是本项目的云层烘焙思路。

你可以按这个顺序理解：

1. 游戏准备天空、太阳、云量等参数。
2. GPU运行云着色器，计算图片中每个像素的云效果。
3. 结果写入内部的云纹理。
4. 天空渲染读取这张纹理，把云显示到场景里。

“烘焙”不意味着结果永远不再更新。本项目有自己的更新调用，不能理解成安装时生成一次、以后完全没有成本。这里重点讨论启动阶段的压力。

## 3. “负载过高”到底高在哪里？

首先，要计算的像素多；其次，每个像素的云效果也要经过计算；启动时还有其他渲染准备任务，这些工作可能集中在同一个时间段。

可以把它想象成餐厅厨房：单独做一道复杂的菜可能没问题，但很多菜同时开做，就可能忙不过来。本次单独运行环境渲染实验没有直接复现故障，完整游戏启动却曾经出现GPU重置，因此我们关注的是**组合任务带来的瞬时压力**。

“负载过高”是对现象和当前证据的概括，并不是日志已经证明某个百分比超过固定上限。它也不能直接等同于手机发热、内存用完或着色器语法错误；这些结论都需要各自的证据。

## 4. 为什么会卡进度条、闪画面，甚至初始化失败？

正常情况下，游戏提交绘制任务，GPU完成计算，WebView显示新画面。

本次故障记录里，更早出现的是GPU上下文重置，之后才出现图形资源、画面合成和着色器链接错误。“上下文”可以理解为游戏与图形系统之间的一套工作状态；它异常后，后续绘制就可能无法正常完成。

你可能看到：

- 进度条停住，画面闪动或继续显示旧画面。
- 游戏内部认为已经就绪，但手机画面没有正确更新。
- 出现“图形初始化失败”，随后退出游戏。

所以，看到“搭建广场中”不能直接认定广场模型有问题。进度条表示当时显示的阶段，真正的错误要结合系统日志和截图判断。

项目已经增加失败拦截和Android原生提示，避免异常后继续进入游戏。提示框是故障保护，降低实际负载才是这次尝试的修复措施。

## 5. 这次具体改了什么？

只缩小手机内部的云烘焙图片，PC继续使用原尺寸。

| 项目 | 原尺寸 | v1.0.17尺寸 |
| --- | --- | --- |
| 手机云纹理 | 2048 × 640 | 512 × 160 |
| PC云纹理 | 2048 × 640 | 2048 × 640 |

我们一起算一下：

```text
原图：2048 × 640 = 1,310,720 个像素
手机新图：512 × 160 = 81,920 个像素
81,920 ÷ 1,310,720 = 1/16
```

宽和高都缩到原来的四分之一，总像素数就变成原来的十六分之一。

**1/16指这张内部图片的像素数量，不代表整个游戏快16倍，也不代表全部GPU耗时下降到1/16。** 人物、场景、抗锯齿等仍需要计算。

代码同时让尺寸参数、分条绘制范围与新图片尺寸一致，避免缩图后仍按旧尺寸计算或绘制。云着色器和纹理格式未在本批更换。

## 6. 为什么保留2倍高清，云图却可以变小？

它们控制不同的东西：“2倍高清”控制游戏画面的渲染像素密度；“云纹理尺寸”控制天空内部使用的一张素材图。

你可以想象一张高清照片里有一幅远处的壁画：照片整体可以很清晰，壁画本身的细节多少则由壁画素材决定。

这次调整后：

- 手机仍保持固定2倍高清和SMAA抗锯齿。
- 本次没有降低人物、椅子模型精度，也没有减少原来的8人对局人数。
- 手机云彩的小细节可能减少、看起来更柔和，这是局部取舍。
- PC云纹理仍为2048 × 640，保留原有设置。

这次改动不用于解决人物或椅子模糊。如果它们仍然模糊，要另查实际渲染分辨率、模型材质、后处理等因素。

## 7. 如何确认这次调整有效？

只看一次成功启动还不够，所以这次分步验证：

1. **运行最简单的图形页面。** 不加载完整游戏，检查基础画图。最终连续3次通过，说明这台手机在测试时能够运行基础图形内容。
2. **隔离环境渲染。** 带云和不带云的环境实验均未直接触发重置，但带云实验出现约1.65秒GPU/窗口等待，因此继续调查完整启动的组合压力。
3. **只改变手机云图尺寸，再启动完整游戏。** 最终3次完整冷启动通过，就绪约10.6～11.3秒，USB截图正常，本轮关注的GPU重置、死锁、SharedImage异常和着色器失败均未记录到。
4. **跑一局60秒Boss战。** 加入自动移动、瞄准、开火等游玩操作，等待对局结束，确认没有初始化或切场景图形失败。
5. **上传日志并关闭游戏。** 核对电脑收到对应版本日志后关闭游戏，完成测试闭环。

这里“冷启动”指关闭游戏进程后重新启动，不是给手机降温，也不是清空存档。

测试设备：HONOR ALP-AN00、Adreno 730、Android 14、WebView 131.0.6778.260。证据支持启动环境组合负载峰值与故障有关，降载后本轮未复现；还不能精确证明驱动内部机制，也不能保证所有手机都已覆盖。

## 8. 现在已经稳定30帧了吗？

**还没有。启动正常与实战稳定30帧是两项验收。**

本轮Boss实际采样约62.38秒，平均26.18FPS，仍有7个达到或超过100毫秒的帧间隔。因此，可以记录“本轮初始化修复验证通过”，不能记录“稳定30帧通过”。

30FPS意味着平均每秒显示30帧，每帧大约只有33.3毫秒。如果偶尔一帧花100毫秒，就可能感到明显顿挫。平均帧率接近目标，也不代表每一帧都稳定。

后续仍需按“一局一分钟 → 分析日志 → 修改一个问题 → 提交 → 再测试”的方式优化。长期发热后的表现需要另做较长时间验证。

## 9. 再次异常时，你应该怎么做？

1. 记下游戏版本，以及异常发生在启动、进Boss还是战斗中。
2. 截图或录屏，尽量保留提示内容、进度条和时间。
3. 如果诊断入口还能操作，上传日志。USB上传成功后，电脑文件位于项目的 `releases/logs/`。
4. 如果提示“USB接收未就绪”，确认手机已授权，再在项目根目录运行下面的命令恢复通道：

   ```powershell
   ./tools/start-usb-debug.ps1
   ```

5. 如果出现原生“图形初始化失败”窗口，按提示退出。反复重启后偶尔成功，不代表故障已经修复，需要保留日志判断。

排查时要结合游戏日志、Android系统日志和真实截图，区分渲染失败、上传连接失败和截图采集失败。
