# v1.0.10 / test10：手机首帧与开局角色预热第二批优化

更新日期：2026-10-24（北京时间）。本批接续[启动与菜单test9](STARTUP-test9.zh-CN.md)，优先处理加载收尾和开局集中工作，不把本批实现视为真机性能验收。

## 真机依据与问题定位

v1.0.9收到的设备为华为PLA-AL10 / Maleoon920 / 华为WebView114。启动到可交互记录为25.771秒；93%到Ready区间为3.625秒，v1.0.8对应区间为22.581秒。这是两次运行的观察值，没有控制设备温度、缓存等条件，不能当作严格性能对照。

v1.0.9仍记录到`startup-full-frame`耗时3598ms，以及真实开局期间2283ms、2452ms和2004ms的长任务。完整帧调用包含模拟、角色LOD、材质与绘制准备、界面等工作，3598ms不能直接归因于纯GPU渲染。单个长任务和定时器响应延迟都不是Android系统ANR线程堆栈；这些日志不能证明无响应等待框已消除或已经确定其全部原因。

代码复核发现，逐对象真实绘制会触发角色相机钩子，使`_rendered`变为true。接下来的完整帧在`_updateLod()`中触发`warmAll()`兜底，标题/菜单演示的多个角色因此再次集中构建全部LOD与隐藏材质。原`warmAll()`在首次await前就构建三档网格及抖动替身；原开局流程又同时调用多个角色，不能仅靠函数名中的async避免主线程停顿。

这台设备没有`KHR_parallel_shader_compile`。本地固定Three.js的`compileAsync()`仍先同步调用`compile()`，且首次`getUniforms()`/`getAttributes()`才可能承担链接状态检查和接口枚举。只把`compileAsync()`分次调用，仍可能把首次程序准备留给实战。

## 本批处理

- **菜单演示**：手机attract对局不再自动触发所有角色的完整`warmAll()`，继续按当前实际可见对象预热。真实对局仍会显式准备各角色；运行期新出现角色保留串行兜底入口。PC保持原自动条件。
- **角色准备**：真实对局中的8个角色共用手机串行队列。入队立即设置`_warmed`，重活开始前先经过rAF和普通任务让出浏览器；逐LOD构建、逐武器远景几何准备，普通材质与淡出/淡入变体逐网格编译，每步之后再次让出线程。人数和模型档位策略不变。
- **真正隔离编译输入**：Three.js的`compile()`会遍历隐藏子树，不能仅改变visible来限制编译。手机为当前单个网格创建不挂回游戏场景的`clone(false)`代理，保留蒙皮类型/骨架，按实战HDR渲染目标准备程序；同步调用结束立即恢复原渲染目标。
- **完成首次程序准备**：每个编译小步await后，只对当前材质的`currentProgram`调用`getUniforms()`和`getAttributes()`，不关闭shader错误检查，不扫描全场景程序。`prepareMobileMaterialPrograms()`支持材质数组及程序去重，记录准备数量和程序增量。此处依赖仓库固定的本地Three.js内部接口，升级vendor后需要重新检查。
- **退出与取消**：角色离开原父节点、切换场景/对局、销毁或开局准备令牌取消/被替换时，停止后续小步。异步编译等待结束后先检查有效性，再访问材质，避免取消后使用已释放资源。联机准备令牌另核对`G.net.match`身份；后台直接离房即使未调用游戏退出，也不能继续旧预热或重新bind已销毁对局。代理不会改变真实角色可见性；异常时也恢复渲染目标、阴影更新标志。
- **准备期互斥**：手机从开局入口立即建立准备令牌，防止重复点击造成并发换图/开局。准备期主循环暂停比赛模拟与绘制，保留网络心跳和输入清理。退出先取消令牌并等待当前建造/编译安全结束，再建立菜单演示世界，避免旧任务覆盖新场景。
- **Boss**：手机等待模型资源就绪后，按单网格代理逐次编译，使用HDR目标并完成首次程序准备；每步检查取消、恢复目标并让出线程。PC保留原准备路径。
- **联机就绪握手**：手机通过`waitForReady`能力字段告知房主采用严格准备模式。有手机参与时，房主等待仍在房间中的真人客户端全部ready，避免12秒兜底在慢设备预热未完成时强行开始；手机若先收到go则延后到本机准备/bind完成。退出、掉线或旧局迟到结果不得再次报告ready或启动旧比赛。纯PC房间保留原12秒兜底策略。所有参与端需使用本批新会话代码；旧版房主忽略能力字段时仅保证新手机本地bind前不启动，不承诺跨旧版房主全房同步。

固定2倍高清、SMAA、60FPS目标及默认关闭自动降清晰度保持原要求；不减少对局人数，不改变模拟或命中规则。PC原画面与准备路径保持原实现。分批会增加让帧和调度等待，开局总耗时可能变长；本批目标是减少集中连续工作并获得可定位的证据，不能保证总加载时间缩短。单次LOD建模、shader链接或驱动调用仍不可中断，不能承诺每个设备都无长任务。

## 日志阅读方法

- `current.startup.stages`中的`startup-prime-*`与`startup-frame-*`分别记录模拟初始化和完整收尾帧的九段：`input`、`simulation`、`effects`、`environment`、`camera`、`paint`、`prepare`、`draw`、`ui`。结合`startup-simulation-prime`、`startup-full-frame`总段判断集中工作实际落在哪一段，避免把整帧时间当作GPU时间。
- `mobile-character-tier-build`、`mobile-character-weapon-far`、`mobile-character-material-compile`、`mobile-character-shadow-warm`记录角色各小步；编译段含`programsAdded`与`programsPrepared`。`match-character-warm`、`match-character-warm-total`和`match-boss-warm`提供开局角色/Boss上下文。
- 开始可交互后，阶段记录进入`current.responsiveness.operations`，保留最近40项；新增`operationCount`记录累计项数，`slowOperations`保留耗时至少200ms的最慢20项，防止前面的重步骤被后续缓存命中覆盖。
- 每角色另记录`mobile-character-warm-summary`事件，包含排队等待、总耗时、步骤数、最慢步骤、各类步骤聚合、程序增量，以及取消/失败状态。事件保存在`current.events`中，detail为JSON文本；原始事件仍有容量上限，不是无限性能追踪。
- 阶段耗时可能含异步编译等待和调度，不等同纯CPU耗时；整帧绘制提交耗时也不是GPU完成耗时。Long Tasks和前台心跳记录继续保留，系统ANR仍需Android线程/系统记录辅助判断。
