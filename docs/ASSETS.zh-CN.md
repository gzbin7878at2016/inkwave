## 1. 先颠覆一个认知:这里的"资产"是代码

传统游戏(UE4/Unity)的资产流:

```
美术在 DCC 里制作 ──► 导出 FBX/PNG ──► 导入引擎序列化(.uasset)
                                    ──► Cooking 压缩转换 ──► 运行时加载解压 ──► 显存
```

INKWAVE 的资产流:

```
作者写 JS/GLSL 代码 ──► 游戏启动时(或首次用到时)执行这段代码 ──► 直接生成网格/纹理/声音 ──► 显存/声卡
                                    ↑ 全程没有文件落地
```

**资产 = 一段"展开后能变成模型/贴图/声音"的配方代码。** 加载条上那些时间(见 [BOOT.zh-CN.md](BOOT.zh-CN.md)),很大一部分就是"执行配方"的耗时。

### 为什么这样做?(架构决策,摘自 ARCHITECTURE)

| 收益 | 说明 |
|---|---|
| 零下载 | 除两个字体和烘焙 AO 图外,没有任何静态资源,仓库极小、打开即玩 |
| 定制渲染的前提 | 墨水系统需要"逐滴湿度、墨面高度场"——**外部美术资产无法表达这种数据**,只有代码生成的材质能做到 |
| 参数化变体 | 同一套"配方"换参数就是新内容:12 把武器、几十种发型服装、全部来自同一批生成函数 |
| 版本友好 | 资产和代码同在一个 git 仓库,改生成算法 = 改资产,无"资产版本对不上代码"的问题 |

代价也诚实地说:**生成算法本身成了最难维护的"美术资产"**,且无法享受到美术工具的所见即所得。

## 3. 共同的工程模式(看懂这四条线的钥匙)

四条生产线表面各异,背后是同五个模式。先在总览里建立,专文里你会反复见到它们:

```
① 配方函数      资产 = buildXXX(参数表) 的纯函数;参数不同,产物不同
② 注册表        生成的资产挂进 registry(武器 kits / SFX 表 / 材质表),运行期按名取用
③ 对象池        运行期不 new:加载/首次用时建好池,游戏中复用(main.js 的 _warmup 就是干这个)
④ 惰性创建      首次用到才生成 + 预热阶段统一"演一遍",防游戏中途卡顿
⑤ 降级容错      生成失败给假实现(stubs)/兜底材质,游戏永不因资产缺失而崩
```

## 4. 与传统管线的逐项对比(学习定位用)

| 环节 | UE4 传统管线 | INKWAVE |
|---|---|---|
| 建模 | Blender/Maya 手工 | `character-geo.js` 等代码"捏" |
| 动画 | 关键帧剪辑(.uasset) | **无剪辑**:每帧代码算骨骼姿态(见 RIG 专文) |
| 贴图 | 手绘/扫描 PNG | Canvas 2D / GPU 逐纹素烘焙 |
| 音频 | 录制 wav/ogg | Web Audio 振荡器实时合成 |
| 导入设置 | 导入器面板调参 | 没有"导入"这一步;参数就在 config.js |
| 版本控制 | 二进制资产 + 专用 diff | 纯文本代码,git 原生 diff |
| 运行时加载 | 异步包流送、解压 | 同步调用生成函数(或预热期生成) |

> 🎯 给 UE4 学习者的定位建议:这个项目的资产系统回答了一个好问题——"**引擎里那些黑盒环节,如果全用手写代码复刻,长什么样?**" 读完这个系列再回头看 UE4 的 Persona/材质编辑器/音频蓝图,你会知道每个面板背后真正发生的事。
